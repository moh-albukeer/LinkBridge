# مواصفات بروتوكول LinkBridge الموحد (LB01 v1.0)

يفصل بروتوكول **LinkBridge v1.0** بشكل كامل بين منطق الحافظة والملفات وبين وسيلة النقل الفيزيائية (`TransportAdapter`)، ويدعم ثلاثة مسارات اتصال:
1. `WIFI_LAN` (عبر TCP + TLS 1.3/1.2)
2. `WIFI_HOTSPOT` (عبر TCP + TLS 1.3/1.2)
3. `BLUETOOTH_RFCOMM` (عبر Bluetooth Classic RFCOMM + تشفير تطبيقي `ECDH P-256 + HKDF-SHA256 + AES-256-GCM`)

---

## 1. ترويسة الإطار الموحد (64 بايت ثابتة — Big-Endian)

كل إطار يُرسل عبر أي مسار يبدأ بترويسة ثنائية طولها **64 بايت** بترتيب شبكي (`!4sBBHQQQ32s`):

| الإزاحة (Offset) | الحجم | الحقل | الوصف |
| :--- | :--- | :--- | :--- |
| `0..4` | 4 بايت | `magic` | البايتات الثابتة `b"LB01"` للتحقق من هوية البروتوكول |
| `4..5` | 1 بايت | `version` | إصدار البروتوكول (`0x01`) |
| `5..6` | 1 بايت | `flags` | رايات الإطار: `0x01 = ENCRYPTED_AEAD`، `0x02 = REQUIRE_ACK`، `0x04 = IS_BINARY_CHUNK` |
| `6..8` | 2 بايت | `msg_type` | نوع العملية (`MessageType` uint16) |
| `8..16` | 8 بايت | `msg_id` | معرّف الرسالة التسلسلي (uint64) |
| `16..24` | 8 بايت | `transfer_id` | معرّف عملية نقل الملف (`0` لرسائل التحكم والحافظة) |
| `24..32` | 8 بايت | `payload_length` | طول الحمولة المرسلة بالبايت (uint64) |
| `32..64` | 32 بايت | `sha256_digest` | بصمة SHA-256 الخام (32 بايت) للحمولة قبل التشفير للتحقق من سلامة كل إطار |

تلي الترويسة مباشرةً حمولة بطول `payload_length` بايت.

---

## 2. فصل رسائل التحكم عن تدفق كتل الملفات

- **رسائل التحكم والحافظة (`IS_BINARY_CHUNK = 0`)**: تكون حمولتها كائن JSON مرمّز بـ UTF-8 بحد أقصى 1 ميجابايت.
- **كتل الملفات (`MSG_FILE_CHUNK = 0x23` مع `IS_BINARY_CHUNK = 0x04`)**: تحمل البيانات الثنائية الخام للكتلة مباشرة دون تحويل إلى Base64، مما يحافظ على السرعة الكاملة للشبكة ويقلل استهلاك المعالج والذاكرة.
- **حجم الكتلة القياسي**:
  - عبر Wi-Fi / Hotspot: **64 KiB** (`65,536` بايت).
  - عبر Bluetooth RFCOMM: **16 KiB** (`16,384` بايت) لملاءمة مخازن RFCOMM ومنع اختناق القناة.

---

## 3. مراحل الاقتران والمصادقة وإنشاء الجلسة

1. **`HELLO (0x01)` و`HELLO_ACK (0x02)`**:
   يتبادل الطرفان المعرّف `device_id`، والاسم، وشهادة X.509 بصيغة PEM، وبصمتها `SHA-256`، وقيم Nonce عشوائية (`client_nonce` و`server_nonce`)، والمفتاح العام المؤقت `ECDH P-256`.
2. **الاقتران الأولي (`PAIR_REQUEST 0x03` / `PAIR_RESPONSE 0x04`)**:
   إذا لم يكن الجهاز مقترنًا مسبقًا، يحسب الطرف المبادر إثبات حيازة رمز الاقتران:
   `HMAC-SHA256(key=PIN_or_QR_Secret, msg=initiator_id|initiator_fp|responder_id|responder_fp|client_nonce:server_nonce)`
   وعند نجاح التحقق، يشتق الطرفان مفتاح ربط دائم (`link_key` بطول 256 بت) عبر `HKDF-SHA256` مرتبط ببصمتي شهادتي الجهازين، ويُبطل رمز الـ PIN فورًا لمنع إعادة استخدامه.
3. **تفعيل تشفير القناة على Bluetooth RFCOMM (`AeadChannelCipher`)**:
   لا يعتمد LinkBridge على تشفير Bluetooth وحده؛ بل يدمج السر المشترك الناتج عن `ECDH P-256` مع `link_key` عبر `HKDF-SHA256` لإنتاج مفتاح جلسة `AES-256-GCM`، وتُشفّر كل رسالة لاحقة مع رقم تسلسلي تصاعدي يمنع هجمات الإعادة (Replay Attacks).
4. **مصادقة الجلسة (`AUTH_SESSION 0x05` / `AUTH_RESULT 0x06`)**:
   يثبت العميل ملكيته لـ `link_key`، فيصدر الخادم رمز جلسة قصير العمر (`session_token` صالح لمدة ساعة واحدة) يجب إرفاقه في رسائل التحكم اللاحقة.
5. **نقل الملفات والاستئناف (`FILE_OFFER 0x20` -> `FILE_ACCEPT 0x21` -> `FILE_CHUNK 0x23` -> `FILE_COMPLETE 0x25` -> `FILE_VERIFY_RESULT 0x26`)**:
   يفحص المستقبل وجود ملف مؤقت `.lbpart` مطابق لنفس `transfer_id` و`sha256`، ويعيد إزاحة الاستئناف `resume_offset` في رسالة `FILE_ACCEPT` ليكمل المرسل من النقطة التي توقف عندها دون إعادة إرسال الكتل السابقة.
